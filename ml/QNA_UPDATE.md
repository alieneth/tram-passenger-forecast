# ML после экспертной сессии

Документ описывает соответствующий этап экспериментов. Текущий выбранный выпуск и полный пакет: [FINAL_DELIVERY.md](FINAL_DELIVERY.md); актуальное закрытие требований: [REQUIREMENTS_AUDIT.md](REQUIREMENTS_AUDIT.md).

Уточнения получены 26.09.2026. Этот документ уточняет ML-часть предыдущей спецификации.
Исходный выпуск `ml.champion` сохранён для воспроизводимости; новый локальный выпуск — `ml.qna`.

## Принятые правила

1. Обучаются и оцениваются девять маршрутов: 1, 7, 11, 12, 17, 25, 26, 28, 50.
   №5 исключён из модели, метрик и таблицы прогнозов PostgreSQL. В полном конкурсном CSV
   остаются 1464 нуля для №5. `route_availability.json` передаёт `status=no_data`;
   нули CSV не означают прогноз отсутствия пассажиров.
2. По уточнению границы технических часов зануляются **01, 02, 03, 04** в прогнозе, а из обучающих строк они исключаются.
   Час **05 сохраняется полностью**. Исходные labels не перезаписываются; валидация содержит
   исходный `raw_boardings` и очищенный `boardings`. Публикуются обе оценки качества.
3. Восстановление провалов — отдельная проверяемая гипотеза. Детектор сравнивает объём
   дня с медианным часовым профилем того же дня недели за предыдущие 56 суток.
   Нужны минимум четыре аналогичных дня, ожидаемый объём от 1000,
   наблюдаемый объём менее 15% ожидаемого и не более 25% активных нетехнических часов.
   Особые календарные дни пропускаются. Восстановленные значения не становятся
   наблюдаемым фактом и не заменяют target проверочного периода.
4. `pass_route` относится к взаиморасчётам перевозчиков и исключён из признаков.
   Хеш карты не используется для идентификации пассажира, построения поездок или удержания:
   при оплате телефоном он нестабилен. Признаки наблюдаемых выходов и тарифов сохраняются
   в отдельной raw-витрине, но не добавлены автоматически в выбранную модель.
5. День отдаётся по часам, неделя и месяц — по дням. В действующем SQL/OpenAPI нет `week`:
   недельный экран читает семь суточных строк `horizon=month` на маршрут.
   Год — необязательная возможность за дополнительные баллы; точный годовой прогноз не заявляется.
6. Прогноз и границы интервалов — неотрицательные целые. День и месяц имеют отдельную
   калибровку ошибок; суточный интервал не получается механическим сложением почасовых границ.
7. Доступ в интернет разрешён: повторное обучение поддерживает `--online`.
   Инференс работает с замороженными внешними признаками без обязательной сети.
   Фактическая погода будущего периода не подключается; отсутствие штрафа за утечки
   не меняет временной доступности признаков и не делает диагностическую оценку независимой.

MAE нового выпуска: **104,610276** на исходных labels и **104,243245** на очищенной цели.
Средний baseline на очищенной цели: **133,064382**. Это сентябрь–октябрь,
13 176 строк девяти маршрутов; период ранее использовался при разработке.
Метрика платформы после обработки технических часов неизвестна: улучшение очищенной
оценки не выдаётся за измеренный прирост скрытого score.

Выбор восстановления сделан на июле–августе с обучением до 30 июня.
В доступной этому выбору истории подходящих провалов не найдено; оба варианта дали
одинаковую MAE **148,157557**. Поэтому в основном выпуске автоматическое восстановление
**не включено**. В полной истории обнаружены четыре кандидата №50:
7, 14, 21 и 27 сентября. Они сохранены для разбора и возможной отдельной версии;
причина каждого провала не установлена. Ремонт может означать реальное снижение спроса,
а потеря связи — потерю наблюдений: эти ситуации нельзя безусловно приравнивать.

Целевое покрытие интервалов — 80%. Калибровка на сентябре, проверка на октябре:
**81,24%** для часов и **77,78%** для суточных сумм. Для финального прогноза
радиусы пересчитаны по ошибкам сентября–октября. Это эмпирические интервалы;
сдвиг распределения не позволяет гарантировать заданное покрытие будущего периода.

## Воспроизведение

Из корня репозитория; `ML_DATA_DIR`, `ML_CACHE_DIR`, `ML_THREADS` задаются окружением.

```bash
python -m pip install -r ml/requirements.txt
python -m ml.qna train --online
python -m ml.qna verify
python -m ml.qna predict --horizon day --start 2025-11-14 --end 2025-11-14
python -m ml.qna predict --horizon week --start 2025-11-10 --end 2025-11-16
python -m ml.qna predict --horizon month --start 2025-11-01 --end 2025-11-30
```

Файлы создаются в `ml/artifacts/qna_final/`, вне git:

- `test_submission.csv`: ровно `route;date;hour;prediction`, 14 640 строк;
- `bundle.joblib`, `manifest.json`: обученная модель и контрольные суммы;
- `forecast.csv`: 13 176 почасовых и 549 суточных строк девяти маршрутов, ровно поля адаптера SQL;
- `model_version.json`, `model_quality.csv`: метаданные и MAE модели/baseline по маршрутам и в целом;
- `route_availability.json`: отсутствие данных №5;
- `validation.csv`, `interval_validation_*.csv`, `*_gap_candidates.csv`,
  `external_provenance.json`: диагностика и происхождение признаков.

Старый сабмит `ml/artifacts/champion/submission.csv` не изменяется.
Каталог нового выпуска неизменяемый: повторное обучение требует другой `--directory`.
Манифест контролирует целостность собственных локальных файлов и не является подписью
доверенного издателя; произвольные чужие pickle-файлы загружать нельзя.

## PostgreSQL и границы ответственности

`python -m ml.qna save-db` записывает неактивную версию, прогнозы и `model_quality`.
`--activate` явно переключает активную версию в общей транзакции. DSN берётся только
из `ML_DATABASE_URL`. Эти команды не выполнялись на действующей БД.
Схема SQL не меняется; `trams_on_line=NULL`, поскольку будущий план выпуска неизвестен.
Аналоги №5 больше не нужны; фиктивные строки `route_analog` не создаются.
Вклады `factor_contribution` ещё не сформированы: feature importance не заменяет `effect_pct`.

Чистая функция `ml.qna.serving.apply_manual_coefficients` принимает коэффициенты погоды,
трафика, события и календаря, пересчитывает прогноз и границы без повторного обучения.
Её результат — пользовательский сценарий; исходные показатели качества к нему не относятся.

HTTP-авторизация, межсервисная авторизация, файл доступа жюри, карта, тёмная тема и навигация
относятся к backend/frontend. Python не поднимает HTTP-сервис, не хранит пароль жюри
и не меняет чужие модули. Для backend: №5 показывается как «нет данных», недельный
экран использует дневную детализацию. Учётные данные жюри должны передаваться отдельным
непубличным файлом, не коммититься в ML-репозиторий.
