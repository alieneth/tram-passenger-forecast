# Контекст проекта для Claude — Хакатон МТ, «ИИ-прогноз загрузки трамвайных маршрутов»

Этот файл — общий контекст команды. Его загружает в своего Claude каждый участник, чтобы все работали
по одним правилам. В репозитории этот файл лежит в корне как `CLAUDE.md` — Claude Code читает его автоматически. Документы из таблицы раздела 10 — в архиве команды у Дмитрия.

**Правило для Claude:** не придумывай своих названий полей, форматов и допущений. Всё, что описано ниже, —
договорённость команды. Если нужно отступить — сначала скажи об этом человеку.

## 2. Задача в двух словах

Заказчик — ЕДЦ ГУП «Московский метрополитен», пользователь — диспетчер.
Нужно: **прогноз числа входов пассажиров по трамвайному маршруту на каждый час** + веб-сервис с тепловой
картой Москвы, API и выгрузкой, в Docker.

- Горизонты: **«День»** (по часам) и **«Месяц»** (по дням). «Год» не требуется (подтвердили организаторы).
- Проверка точности — **автоматическая на платформе** по файлу сабмита. Метрику уточняем (вероятно MAE).
- Главный критерий от организаторов: **учёт внешних факторов** — чем больше, тем лучше.

## 3. Данные (локально в папке `data/`, в git не попадает)

| Файл | Период | Строк | Что внутри |
|---|---|---|---|
| `train.csv` | 01.01–31.08.2025 | 49 051 926 | Сырые валидации (одна строка = одно прикладывание карты) |
| `test.csv` | 01.09–31.10.2025 | 13 391 571 | То же |
| `labels/labels_day_train.csv`, `labels_day_test.csv` | янв–авг / сен–окт | 46 234 / 11 317 | Цель: `route;date;hour;boardings` |
| `test_submission.csv` | 01.11–31.12.2025 | 14 640 | Шаблон ответа: `route;date;hour;prediction` |
| `spravochniki/*.xlsx` | — | — | Маршруты, остановки с координатами, порядок остановок, образцы расписания и нарядов |

**Разделитель во всех CSV — точка с запятой `;`.**

Поля валидаций: `tran_no; device_no; tran_date_time; begin_date_time; input_date_time; crd_hashcode;
validation_result; tran_type_id; place_id; good_type; pass_route; ngpt_route; bus_exit_no; garage_number`.

Важное про поля:
- `boardings` = число строк с **`validation_result = 1`**, сгруппированных по **часу `tran_date_time`**. Проверено: совпадает с labels.
- `ngpt_route` — текст «25 трамвай» → номер маршрута = число из текста.
- `place_id` — **площадка депо, НЕ остановка** (5 значений). Остановки входа в данных нет.
- `bus_exit_no` — номер выхода (график трамвая) → число трамваев на линии в час.
- `garage_number` — гаражный номер вагона (= `depot_number` в листе «Наряд»).
- `crd_hashcode` — хэш карты; `good_type` — тариф; `pass_route` — цепочка пересадок («Мосметро.НГПТ» = пришёл из метро).
- GPS/телематики в датасете **нет**. Выходов пассажиров **нет**.

## 4. Ловушки датасета

1. **Маршрут 5** есть в сабмите, но в train/test/labels **нет ни одной строки** → прогноз по аналогам (1, 7, 11, 12 — у них есть и история, и координаты), ошибку метода проверяем «с исключением».
2. **Справочник не совпадает с данными:** в справочнике маршруты 1, 2, 3, 4, 5, 6, 7, 10, 11, 12; в данных 1, 5, 7, 11, 12, 17, 25, 26, 28, 50. Для **17, 25, 26, 28, 50 нет координат** — запрошено у организаторов.
3. Расписание и наряды — **только образцы по 15 строк** — запрошено.
4. Сабмит требует **все 24 часа (0–23)**, включая ночь.

Маршруты проекта: **1, 5, 7, 11, 12, 17, 25, 26, 28, 50**.

## 5. Договорённости по форматам (единые для всех)

| Что | Как |
|---|---|
| Номер маршрута | целое число: `route` (не route_id, не routeNumber) |
| Дата | `date`, ISO `YYYY-MM-DD` |
| Час | `hour`, целое 0–23 |
| Факт | `boardings` — пассажиров (входов) в час |
| Прогноз | `prediction`, границы коридора `lower`, `upper` |
| Горизонт | `horizon`: `day` или `month` |
| Время | московское, без часовых поясов в данных |
| CSV | разделитель `;`, числа без пробелов, UTF-8 |
| Единица в интерфейсе | «пассажиров в час» и «пассажиров на трамвай». **Процентов загрузки нет** — выходов в данных нет |
| API | префикс `/api/v1`, контракт — в `openapi.yaml` (готовит Дмитрий) |

## 6. Бизнес-правила и допущения

1. Прогноз на уровне **«маршрут × час»**; остановка/участок — только если дадут расписание.
2. **Праздники и переносы выходных — обязательные признаки.** В периоде прогноза: 3–4 ноября, 31 декабря, предновогодняя неделя (сверить с производственным календарём 2025).
3. **Без утечки из будущего:** для «Дня» — прогноз погоды на момент прогноза, для «Месяца» — климатическая норма. Фактическую погоду ноября–декабря в модель не подавать.
4. **Базовая модель** для сравнения — среднее за тот же час и день недели.
5. **Прогнозы считаются заранее** (пакетно) и кладутся в хранилище; API только читает → иначе не выдержать p95.
6. Решения: предлагать переброску выходов **только между маршрутами одного депо**; норма пассажиров на трамвай — один настраиваемый параметр (по умолчанию 150); при изменении числа трамваев поток считаем неизменным.

## 7. Нефункциональные требования организаторов

- Сотни RPS, **p95 < 200–300 мс**, один контейнер **2–4 vCPU / 2–4 ГБ**, CPU 60–80%, без swap.
- Горизонтальное масштабирование (API без состояния).
- Запуск одной командой: **Docker Compose**.
- Понятные сообщения об ошибках API.
- Приём потоковых данных (у нас — эндпоинт + скрипт-имитатор из истории).
- **Результаты производительности обязательно в README.**
- Рекомендуемый стек (не обязателен): Java 17+/Spring, React 19 + TypeScript 5, Python ML (LightGBM), ONNX при Java, PostgreSQL/ClickHouse, MapLibre/Leaflet. **Решение команды (26.09.2026): бэкенд на Java** (Java 21, Spring Boot). ML — на Python. Связка: Python пакетно считает прогнозы и пишет их в БД, Java-API только читает из БД. ONNX для MVP не нужен (модель не вызывается из Java); понадобится, только если захотим считать прогноз на лету (например, «Что если»).

## 11. Единые правила кода

Цель: код четверых людей и четырёх Claude выглядит как код одного человека и стыкуется без переделок.

### 11.1 Структура репозитория

```
/
├── CLAUDE.md              ← этот файл
├── README.md              ← запуск, архитектура, API, производительность
├── docker-compose.yml
├── .env.example           ← все переменные окружения с примерами (сам .env — не в git)
├── docs/
│   └── openapi.yaml       ← контракт API — единственный источник правды для бэка и фронта
├── data/                  ← датасет и выгрузки, в .gitignore (в git не попадает)
├── ml/                    ← Ярослав: признаки, обучение, сабмит, пакетный пересчёт
├── backend/               ← Артём: API, загрузка данных
├── frontend/              ← Сергей: React-приложение
└── sql/                   ← Дмитрий: витрина и запросы анализа
```

Каждый работает в своей папке. Чужую папку меняем только по договорённости.

### 11.2 Общее для всех языков

| Правило | Как |
|---|---|
| Имена в коде | На английском. Никакого транслита (`marshrut` — нельзя, `route` — можно) |
| Комментарии | На русском, коротко: объясняют «почему», а не «что» |
| Поля данных и JSON API | `snake_case` и строго из раздела 5: `route`, `date`, `hour`, `boardings`, `prediction`, `lower`, `upper`, `horizon` |
| Даты и время | ISO: `2025-11-14`, `2025-11-14T08:00:00`, московское время |
| Конфигурация | Только через переменные окружения (`.env`), никаких адресов и паролей в коде |
| Секреты | Ключи и пароли в git не коммитим никогда |
| Магические числа | В константы или конфиг: `PASSENGERS_PER_TRAM_NORM = 150`, а не просто `150` |
| Логи | Через логгер, не `print` / `console.log` в итоговом коде |
| Размер | Функция — одна задача; файл больше ~300 строк — повод разделить |

### 11.3 Python (ML)

- Python 3.11+, форматирование **ruff format** (стиль black, длина строки 100), линтер **ruff**.
- `snake_case` для функций и переменных, `PascalCase` для классов, `UPPER_CASE` для констант.
- Аннотации типов у всех функций.
- Зависимости — в `requirements.txt` с версиями (или `pyproject.toml`).
- Большие данные — DuckDB / polars / pandas по чанкам; весь train.csv (7,6 ГБ) в pandas целиком не грузим.

### 11.4 Java (бэкенд — решение принято)

- Java 21, Spring Boot, стиль Google Java Style, форматирование через Spotless.
- `camelCase` в коде, но JSON-поля — `snake_case` (настроить Jackson `SNAKE_CASE`).
- Контроллеры и DTO — по `docs/openapi.yaml` (можно сгенерировать интерфейсы через openapi-generator, режим `spring`, `interfaceOnly`).
- Прогнозы читаются из таблицы, которую заполняет Python-скрипт Ярослава (`ml/`). Схему таблицы согласуют Ярослав и Артём.
- Сборка — Maven или Gradle (выбирает Артём), тесты — JUnit 5.

### 11.5 TypeScript / React (фронтенд)

- React 19, TypeScript 5 в режиме `strict`, форматирование **Prettier**, линтер **ESLint**.
- Компоненты — `PascalCase.tsx`, хуки — `useSomething.ts`, остальное — `camelCase`.
- Типы данных API — в одном файле `src/api/types.ts`, поля как в `openapi.yaml` (`snake_case`, без переименования).
- Запросы к API — только через один модуль `src/api/`, адрес API из переменной окружения.
- Мок-данные — в `src/mocks/`, строго в формате `openapi.yaml`.

### 11.6 SQL

- Ключевые слова ЗАГЛАВНЫМИ (`SELECT`, `FROM`), имена таблиц и полей — `snake_case`.
- Каждый столбец и условие — с новой строки, алиасы понятные (`v` для validations — можно, `t1` — нельзя).
- Каждый запрос в своём файле `sql/NN_nazvanie.sql` с комментарием в начале: что считает и зачем.

### 11.7 Git

- Ветка `main` — всегда рабочая. Работа — в ветках `имя/задача`: `artem/api-2-forecast`, `sergey/ui-3-map`.
- Коммиты — в формате `тип(ID задачи): что сделано`, по-русски:
  `feat(API-2): эндпоинт прогноза по маршруту`, `fix(UI-3): часы 05–00 на шкале карты`.
  Типы: `feat` — новое, `fix` — исправление, `docs` — документация, `refactor` — переделка без смены поведения, `test` — тесты.
- В `main` — через pull request, хотя бы беглый просмотр кем-то вторым.
- Перед коммитом: форматтер и линтер без ошибок.

### 11.8 Проверка готовности задачи

Задача готова, если: выполнен «Критерий готовности» из бэклога, код отформатирован, линтер чист,
названия полей совпадают с разделом 5 и `openapi.yaml`, в README есть команда запуска, если она поменялась.

### 11.9 Правило для Claude
