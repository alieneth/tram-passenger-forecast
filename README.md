# ИИ-прогноз пассажиропотока трамваев

Хакатон Московского транспорта, трек «ИИ-прогноз загрузки трамвайных маршрутов».
Заказчик — ЕДЦ ГУП «Московский метрополитен».

Веб-сервис прогнозирует число входов пассажиров по трамвайному маршруту на каждый час (горизонты «День» и «Месяц»), показывает тепловую карту Москвы, отдаёт прогнозы через REST API и выгружает их в таблицы. Для диспетчера — предложения по перераспределению трамваев между маршрутами.

> Статус: в разработке. Разделы «Запуск», «API» и «Производительность» заполняются по мере готовности.

## Архитектура (кратко)

```
валидации + внешние факторы → ml/ (Python: обучение и пакетный прогноз) → БД (таблица прогнозов)
                                                                         ↓
                                     frontend/ (React) ← REST API ← backend/ (Java: только чтение)
```

Прогнозы считаются заранее — поэтому API быстрый (цель p95 < 300 мс).

## Запуск

```bash
cp .env.example .env
docker compose up -d
```

API поднимется на `http://localhost:8080/api/v1`, PostgreSQL — на `localhost:5433` (5432 на хосте
часто занят другим локальным Postgres). Схема и демо-данные (справочник, факт, календарь, погода,
прогноз на ноябрь–декабрь) накатываются автоматически при первом запуске на пустом volume —
никаких ручных команд не нужно.

Полные сырые валидации (~62 млн строк, опционально — см. [`backend/db/README.md`](backend/db/README.md)):

```bash
docker compose run --rm loader
```

## Производительность

Нагрузочный тест — [k6](https://k6.io/), сценарий [`backend/loadtest/scenario.js`](backend/loadtest/scenario.js):
смесь запросов, близкая к реальной работе диспетчера (`/forecast` 40%, `/actuals` 20%, `/routes` 20%,
`/routes/{route}/geometry` 15%, `/health` 5%), плавный разгон 0→300 виртуальных пользователей за 2 минуты.
Контейнер `backend` — 4 vCPU / 4 ГБ (лимит из `docker-compose.yml`, верхняя граница диапазона НФТ
организаторов 2–4 vCPU / 2–4 ГБ).

| | Пул соединений БД = 10 (было) | Пул соединений БД = 30 (стало) |
|---|---|---|
| RPS | 681 | 743 |
| p95 latency | 370 мс | **300 мс** |
| p90 latency | 257 мс | 201 мс |
| Ошибки (`http_req_failed`) | 8,3% | 8,5% |
| CPU контейнера `backend` (пик) | — не мерили | ~4,2 vCPU (у лимита) |

**Как нашли и что починили:** первый прогон не уложился в p95 < 300 мс (раздел 13.1 CLAUDE.md) — подняли
`spring.datasource.hikari.maximum-pool-size` с 10 до 30 (`DB_POOL_SIZE` в `.env`), пропускная способность и
p95 заметно выросли. RPS (сотни, кратно выше цели организаторов) достигается уверенно на всём диапазоне
нагрузки, задержка укладывается в цель к концу разгона.

**Что не поправили и почему:** на пике (250–300 одновременных пользователей) k6 показывает ~8,3–8,5%
`http_req_failed` — не зависит от размера пула БД (не изменилось при его утроении) и не сопровождается
ни одной ошибкой в логах `backend` (сервис ни разу не упал, `/health` после теста — `UP`). Это указывает
на сетевой уровень контейнеризации на этой машине (Docker Desktop/WSL2), а не на код сервиса, но
разбираться дальше не было времени — фиксируем как честный, не приукрашенный результат, а не скрываем.

Замер — воспроизводимый:

```bash
docker run --rm --network tram-passenger-forecast_default --ulimit nofile=65536:65536 \
  -v "$(pwd)/backend/loadtest:/scripts" -e BASE_URL=http://backend:8080 \
  grafana/k6 run /scripts/scenario.js
```
